為什麼需要 RAG

先理解 LLM 的知識限制，再看如何把指定文件變成回答時可以使用的 Context。

LLM 的知識來源ContextRetrieval + Generation
Part 1 · 問題

LLM 使用時的常見問題

LLM 回答問題時，主要依靠訓練期間學到的知識，以及這次提問附上的內容。它可以組合、推論資訊，卻不會自動讀取沒有提供給它的文件。

例如新發布的課程公告、個人筆記或未公開的資料，都不能假設模型已經知道。即使缺少依據，模型仍可能產生語氣肯定、看起來合理的回答。

接下來

先看模型的知識如何形成，再看如何讓回答依據指定資料。

Part 1 · 1.1

LLM 的知識從哪裡來

訓練時，模型讀取大量資料並調整參數，學到文字與概念的關聯。生成回答時，它使用這些參數，而不是自動打開一份原始文件。

區別

模型參數不是能逐筆查詢、保留來源與版本的文件資料庫。回答流暢，不代表它查過指定文件。

Part 1 · 1.2

什麼資訊不能假設模型已經知道

問題要求的特定事實，可能沒有可靠地反映在模型參數裡。模型仍可能產生合理語句，但那不等於答案符合指定資料。

資料類型限制
訓練後的新資訊後來發布的公告或更新，不能假設模型已看過。
私有資料未公開的 employee_handbook.pdf 不一定在訓練資料中。
使用者自己的資料個人筆記或上傳的 PDF，需要在這次使用時提供。
細節或特定領域資訊模型可能懂一般概念，卻不知道某文件的條件、數值或版本。
範圍

這裡討論「只用模型本身回答」。若產品另接搜尋或檔案工具，要看那些工具實際找回了什麼。

Part 1 · 1.3

先把相關 Context 提供給 LLM

Context 是模型在本次回答中可讀到的背景資料。若問題是「第 4 次作業要交什麼格式？」，把「作業說明」和問題一起提供，比只給問題更有依據。

如果資料變成數百份文件，就不能每次都全部放進輸入。此時必須先選出可能相關的段落；這一步叫 Retrieval（檢索）。

Part 1 · 1.4

RAG = Retrieval + Generation

定義

在生成答案前，先從外部知識庫找出與 query 相關的資訊，再把找回的內容連同問題提供給 LLM。

核心直覺：不要求 LLM 記住所有知識；需要時，再把相關知識找給它。檢索或生成出錯，答案仍可能錯。

Part 2 · Big picture

一個 RAG 系統分為兩個階段

先將文件整理成可搜尋的資料；收到問題後，再搜尋、取回原文並交給 LLM。文件與問題都要經過相同或相容的 embedding model。

Part 2 · Indexing

提問前：先讓文件可以被搜尋

提問前，先把文件切成片段、轉成向量，建立可搜尋的索引。搜尋時，系統會先找到相近的向量，再取回對應的原文，交給 LLM 作為回答依據。

步驟輸入輸出為什麼需要
Chunking長文件多個文字片段讓搜尋單位更精確
Embedding每個 chunk數值向量讓問題與段落可以比較
Index向量、原文與來源可搜尋的資料結構查詢時找回相近向量及原文
更新

如果文件改了，相關的 chunks、vectors 與 index 資料也需要更新；否則查詢可能找回舊內容。

Part 2 · Chunking

Chunking 決定「搜尋單位」

若把整份長文件當作一筆搜尋結果，少量相關內容會和大量無關內容混在一起；系統也無法只取回真正需要的段落。

Chunk 是可獨立向量化與檢索的文字片段。切段時保留文件名稱、頁碼或位置，才能在找回後查證原文。

小例子

問「作業繳交格式」時，理想的檢索單位是寫有格式的片段，而非整份課程說明。

Part 2 · Chunking

Chunk 太大或太小，都有代價

太大

一個結果含較多 irrelevant information。即使只有一句相關，搜尋也只能拿回整大段，粒度較粗。

太小

完整意思可能被拆開。例如只取到「期限延後」，卻沒取到「延到哪一天」。

判斷標準：一個 chunk 應足以表達可被搜尋、可被讀懂的局部內容。

Part 2 · Chunking

實務上的做法：Overlap

切點可能剛好把一句話或相連的資訊分到兩段。Overlap（重疊）是讓相鄰 chunks 共用一小段原文，使切點附近的內容在兩段中都能被檢索到。

為什麼使用

如果重要資訊落在切點附近，重疊可減少其中一段缺少前後文的機會。

代價是什麼

重複文字會增加索引量，也可能讓搜尋結果出現內容相近的 chunks，佔用提供給 LLM 的空間。

實務上也常先依標題或段落切分，再控制 chunk 長度與 overlap；沒有適用所有文件的固定數值。

Part 2 · Embedding

Embedding 讓搜尋不只依賴相同字詞

Keyword search 主要比對文字是否出現。當問題與文件使用不同詞彙時，即使意思接近，也可能找不到。

資料文字Keyword searchEmbedding search
問題car repair沒有相同關鍵字，可能漏掉語意接近，向量可能靠近
文件automobile maintenance
 
"car repair"              → [0.21, -0.38, 0.72, ...]
"automobile maintenance" → [0.19, -0.35, 0.69, ...]
重點

Embedding model 把文字轉成向量，讓系統可以比較語意。效果仍取決於模型、語言與文件內容，向量接近不代表兩句話完全相同。

Part 2 · Embedding

向量關係取決於模型學過什麼

經典的詞向量例子

king − man + woman ≈ queen

某些 Word2Vec 詞向量模型中，性別與角色的關係可能反映在向量方向上。這是幫助理解的經典例子，不是永遠成立的代數公式。

cat 和「貓咪」會靠近嗎？

不一定。模型必須在訓練時學到中文與英文的對應關係，兩個詞的向量才可能靠近。

若要做中英文混合搜尋，應選擇明確支援多語言的 embedding model，並用自己的問題與文件實際測試。

本課的判斷方式

不要只看模型名稱或單一示例。先確認資料語言與使用情境，再檢查真正相關的 chunks 是否能排到前面。

Part 2 · Index

Index 不只是「存向量」

Vector index（向量索引）組織段落向量，讓 query 到來時能搜尋相近向量。搜尋結果還必須連回 chunk 原文與來源，才能交給 LLM 並供讀者查證。

Vector：[0.21, -0.38, 0.72, ...]　用來比較
Chunk text：「第 4 次作業請繳交 PDF。」　用來回答
Source：assignment_04.pdf 第 2 頁　用來追查

資料少時可逐一比較；資料多時通常需更有效率的搜尋方法。如 FAISS 和 vector database，但此處不細講。

Part 2 · Query time

提問後：向量化、搜尋、取回原文

使用者問題經過與文件端相同或相容的 embedding model，得到 query vector。系統拿它與索引中的 document vectors 比較，按相似度取出若干 chunks。

Document vectors

提問前已計算並建立 index。

Query vector

每次收到問題後，依該問題計算。

Part 2 · Generation

把 Query 與取回的原文一起交給 LLM

Retrieval 選出候選 chunks 後，系統把問題、段落原文與必要來源放入 LLM 的輸入。LLM 再根據這些資料組織答案。

Question: 第 4 次作業要交什麼格式？

Retrieved context:
[assignment_04.pdf, p.2]
第 4 次作業請繳交 PDF。

Instruction: 根據 context 回答，並指出來源。

可能回答

「請繳交 PDF；來源：assignment_04.pdf 第 2 頁。」

限制

如果檢索漏掉關鍵段落，LLM 無法根據未提供的內容作出有依據的回答。

Part 3 · Similarity

Cosine similarity 比較向量方向

Cosine similarity 不是直接量兩個點相隔幾公分，而是把向量看成從原點伸出的箭頭，比較兩支箭頭的方向與夾角：同方向接近 1，垂直接近 0，反方向接近 −1。

cos(θ) = q · d‖q‖ ‖d‖

q：問題的 embedding
d：某個文件 chunk 的 embedding
q · d：對應位置相乘後加總，稱為內積

‖q‖、‖d‖：向量長度。分母把長度影響除掉，使分數主要反映方向。

計算分數是為了排序候選段落；分數不是答案正確率。
例如：問「第 4 次作業要交什麼格式？」，寫著「第 3 次作業請交 PDF」的段落可能得到高分，但它不能回答第 4 次作業的問題。

Part 3 · Numerical example

用二維向量實際算一次

令 q=(1,1)、d1=(1,0.8)、d2=(-1,0)。先算內積與各向量長度，再代入公式。

q 與 d1

內積：1×1 + 1×0.8 = 1.8
長度：‖q‖=√2、‖d1‖=√1.64
cos(q,d1) = 1.8/√3.28 ≈ 0.994

q 與 d2

內積：1×(−1) + 1×0 = −1
長度：‖d2‖=1
cos(q,d2) = −1/√2 ≈ −0.707

因為 0.994 > −0.707，d1 排在 d2 前。

Part 3 · Top-k

Top-k 取排序最前面的 k 段

假設已對每個 chunk 算出相似度。若 k=2，按分數由高到低排序後，只取 A 與 B 的原文。

排名ChunkSimilarityk=2 的結果
1A0.91取回
2B0.84取回
3C0.71不取回
4D0.32不取回

k 太小

可能漏掉回答所需的另一段資料。

k 太大

可能帶入更多無關內容，也增加送入 LLM 的 token 數。

相似分數只決定候選順序，不能驗證片段是否足以回答問題。

Part 3 · Putting it together

把 Embedding、Similarity、Top-k 串起來

下面的 Python-like pseudo-code 對應完整的檢索機制。chunks[i] 與 document_vectors[i] 是同一段資料的原文與向量。

query_vector = embed(query)  # 問題 → 向量
scores = [cosine_similarity(query_vector, v)
          for v in document_vectors]  # 每段計算相似度
top_indices = sorted(range(len(scores)),
                     key=lambda i: scores[i],
                     reverse=True)[:k]  # 排序後取前 k 段
retrieved_chunks = [chunks[i] for i in top_indices]  # 找回原文

這段程式呈現檢索機制；大型索引與資料庫的實作並未包含在內。

Part 4 · Document

LangChain 的 Document：文字與來源

Document 是 LangChain 表示一筆文字資料的物件。在這堂課，一頁 PDF 或切出的一段文字，都可以是一個 Document。

from langchain_core.documents import Document

doc = Document(

)

page_content

這筆資料的文字。切段時會切它；檢索找回後，也會取出它來提供給 LLM。

metadata

描述這筆文字的資訊。除了檔名、頁碼，也可能有 PDF 記錄的標題與作者；下一頁再拆開看。

接到 notebook：PDF 載入後得到每頁的 Document；split_documents() 再把頁面切成較小的 Document，並保留來源資訊。

Part 4 · Document

metadata：文件附帶的描述資訊

metadata 是「欄位名稱 → 值」的對照表，欄位沒有固定清單。載入器會放入它讀到的資訊；我們也可以在程式中加入需要的欄位。

欄位例子記錄什麼從哪裡來

source_file、page_number檔名、給人看的頁碼本課 notebook 加入；page_number 從 1 開始
start_indexchunk 在原頁文字中的起始位置本課切段程式設定產生
實際例子

本課的 python_intro.pdf 文件屬性有標題，Author 值是 RAG practice corpus。其他 PDF 的作者欄可能空白；欄位有值也不代表已核實作者身分。

看程式時注意：page=0 指第一頁；notebook 另存 page_number=1，方便顯示來源。想知道實際有哪些欄位，可印出 doc.metadata。

Part 4 · Metadata filter

metadata 也能用來篩選檢索範圍

除了顯示來源，metadata 也能先排除不符合條件的 chunks，再進行向量搜尋。

# 建立索引時，替文件保存可比較的月份
metadata = {"source_file": "report.pdf", "published_month": 202603}
# $gte = greater than or equal，意思是 >=
result = collection.query(
    query_embeddings=[query_embedding],
    where={"published_month": {"$gte": 202602}},
    n_results=3,
)
搜尋順序

先留下 published_month ≥ 202602，也就是 2026 年 2 月（含）之後的 chunks，再從中取回向量最相近的結果。

資料格式要一致：202602 代表 2026 年 2 月。若有些文件存文字、有些存數字，就無法可靠比較。目前 notebook 尚未加入這個欄位與 filter，這裡展示的是可延伸做法。

Part 4 · Code 3/6

產生 embedding：每個 chunk 對應一個向量

Part 4 · Code 4/6

建立索引：一起保存向量、原文與來源

在 ChromaDB 的 collection（一組可搜尋的資料）中，同一筆 chunk 的文字、來源資訊與向量一起寫入。

collection.add(
    ids=[make_chunk_id(doc) for doc in batch_documents],
    documents=[doc.page_content for doc in batch_documents],
    metadatas=[clean_metadata(doc.metadata) for doc in batch_documents],
    embeddings=batch_embeddings.tolist(),
)

輸入

一批 chunks 和順序相同的一批 embeddings。

輸出

寫入本機索引；之後搜尋到向量時，也能取回對應文字和來源。

這一步不再產生向量：向量已由上一頁算好；這裡負責保存並建立可搜尋的索引。

Part 4 · ChromaDB

ChromaDB 實際保存哪些資料

ChromaDB 是向量資料庫。它不只保存 embedding，也會保存同一筆 chunk 的 ID、原文與 metadata，之後才能從相近向量找回可閱讀的資料。

用向量搜尋

embeddings 用來計算哪些 chunks 最接近問題。

把結果交還給人與 LLM

documents 提供原文，metadatas 提供檔名、頁碼等來源。

Part 4 · Code 5/6

檢索：用問題向量找回相關 chunks

收到問題後，先用同一個 embedding 模型轉成向量，再請 ChromaDB 取回最接近的幾筆資料。

query_embedding = self.embedding_manager.encode([query])[0]
result = self.collection.query(
    query_embeddings=[query_embedding.tolist()],
    n_results=min(top_k, self.collection.count()),
    include=["documents", "metadatas", "distances"],
)

輸入

query 是使用者問題；top_k 決定最多取回幾段。

輸出

documents[0][i]、metadatas[0][i] 與 distances[0][i] 是同一名次的 chunk。程式依相同索引把它們合在一起。

metadata 怎麼回來：ChromaDB 找到第 i 個向量後，會一起回傳寫入時綁在同一筆資料上的原文與 metadata。距離較近仍不保證內容足以回答問題。

rag_input = prepare_rag_input(

問題、檢索器，以及要取回的 chunk 數量。

輸出

rag_input["prompt"] 包含問題、取回的原文和來源標記。

Part 5 · Concepts

RAG、MCP、Agent 分別解決什麼問題

名稱它是什麼在系統中的工作
RAG先檢索資料，再把相關內容提供給模型的流程讓回答能使用外部知識與可追溯的來源
MCP讓 AI 應用連接外部工具與資料來源的標準介面統一描述可使用的工具、資源與呼叫方式
Agent帶有 instructions 與 tools，並可反覆選擇下一步的執行方式判斷何時檢索、何時呼叫工具，以及何時輸出答案
不是三選一

Agent 可以使用 RAG 工具，也可以透過 MCP 連接其他系統。RAG 也能被包成一個 MCP tool，但 RAG 本身不一定需要 MCP。

Part 5 · Integration

Agent 可以在需要時呼叫 RAG

Agent 先讀取問題，再選擇要不要使用工具。若問題需要課程文件，它可以呼叫 RAG；若要查其他系統，也可以透過 MCP 連接對應工具。

Part 5 · Deployment

RAG 可以部署在哪裡

情境原始文件向量與 metadata執行檢索的程式
本機練習電腦資料夾本機 ChromaDBNotebook 或本機程式
應用程式後端伺服器磁碟或物件儲存持久化的 vector database後端 API 服務
雲端服務雲端物件儲存託管式 vector database 或支援向量搜尋的資料庫雲端運算服務或 Agent

搬到雲端時不變的部分

仍然要載入、切段、建立 embedding、保存原文與來源，再依問題檢索。

需要另外決定的部分

資料放在哪裡、誰可以存取、索引何時更新，以及服務能承受多少使用者。

RAG 是一套流程：它可以完全在本機，也可以把儲存、檢索與生成分散到不同的雲端服務。

Part 5 · Data formats

RAG 不只處理文字型 PDF

資料建立索引前先做什麼建議保留的來源資訊
PDF、Word、網頁抽取文字，再依標題或長度切段檔名、頁碼、網址、標題
圖片或掃描 PDF用 OCR 讀文字，或產生圖片描述與影像 embedding檔名、頁碼、圖片位置
音訊語音轉文字，再切成可檢索的片段檔名、開始與結束時間
影片轉錄語音，必要時擷取畫面或產生畫面描述檔名、時間點、畫面位置

相同的是檢索概念，不同的是前處理：系統必須先把每種格式轉成可搜尋的內容，並保留能回到原始資料的位置。
